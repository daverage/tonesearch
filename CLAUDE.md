## Architecture

TONE Search is a Flask app. A user describes a guitar tone; the app returns an AI "tone brief" and TONE3000 NAM (Neural Amp Modeler) packs ranked by AI.

- `app.py` holds the Flask routes, input validation, and per-visitor hourly rate limiting. The limiter stores hits in SQLite at `$TONESEARCH_DATA_DIR/limits.sqlite3` (default `data/`, which is gitignored) and keys visitors by `CF-Connecting-IP` (the first `X-Forwarded-For` entry is client-controlled behind Cloudflare), falling back to the last `X-Forwarded-For` entry. `application` is the WSGI alias that `passenger_wsgi.py` loads for cPanel/Passenger deployment.
- `tonesearch/ai.py` talks to an OpenAI-compatible chat endpoint using stdlib `urlopen` and JSON-schema structured output, validated with pydantic. It is configured through `NAM_MIXER_AI_*` env vars; the provider is `cloudflare` (default), `custom` (https only), or `local` (localhost http only). Each setting can be provider-scoped, e.g. `NAM_MIXER_AI_CLOUDFLARE_MODEL`, with the unscoped name as a fallback. AI tuning also uses NAM Mixer's names (`MAX_TOKENS`, `TEMPERATURE`, `TIMEOUT_SECONDS`, `HISTORY_MESSAGES`, `HISTORY_MESSAGE_CHARS`, `RESEARCH_CHARS`, `MAX_REPLY_CHARS`, `MAX_EXPLANATION_CHARS`). Each value is clamped to `ai.TUNING_LIMITS` and carried on `AiConfig.tuning`. Replies don't have to come from a JSON-mode model. `_chat` tries `response_format` json_schema, then json_object, then no format at all, and remembers the first format each model accepts in `_FORMAT_TIER`. `_ask` adds an example object built from the schema (`_example`). `_decode` and `_repair` find and fix the JSON: fences, `<think>` blocks, trailing commas, Python literals and cut-off replies. `_normalise` maps field aliases and loose values onto the pydantic models. A thinking model that runs out of tokens raises a clear `AiError`. `_chat` asks for `stream=true` and reads server-sent events (`_read_stream`), so `TIMEOUT_SECONDS` limits each wait for data, not the whole reply; endpoints that ignore streaming are read as plain JSON, and ones that reject it are remembered in `_NO_STREAM`. Thinking models (by name, `_THINKING_NAMES`, or once a reply shows reasoning, `_THINKS`) get "think less" hints from `_HINT_TIERS` (`reasoning_effort`, `chat_template_kwargs.enable_thinking`); a 400 steps to the next hint dialect and ends with none, remembered in `_HINT_TIER`. `plan_tone`, `rank_packs` and `ask_about_pack` take a `deadline` (monotonic time); running past it raises an `AiError` that says whether the model was still thinking. Its errors are `AiError`, which is a subclass of `RuntimeError`.
- `tonesearch/research.py` covers TONE3000 search, model listing, and `.nam` downloads (needs `TONE3000_API_KEY`, a `t3k_cs_` secret key). It also has optional DuckDuckGo web research via `ddgs`. `web_notes` runs two searches built from `_search_words` (the request with filler removed, but short requests and names like "Knights of Cydonia" kept whole; `_topic` is separate because it keys the library and cache, so don't change it casually). Two or more `_NEEDS` words search specifications and reviews, one or a model-like token ("AC30") searches one rig and one spec query, none searches two rig queries; bass requests add bass words. It skips sources for three documented reasons (`_UNREADABLE_HOSTS`, `_PRESET_HOSTS`/`_PRESET_PATH`, `_SHOP_HOSTS`, plus listing paths in `_LISTING_PATH`, which leaves `/products/` alone for makers' spec pages), and bass forums (`_BASS_SITES`) unless the request is about bass. Evidence sentences need the request's distinctive words (`_topic_words` drops `_NOT_TOPIC` words such as bass, guitar and tone). Each ddgs search runs in a child process (`_ddgs_search` runs `_DDGS_CHILD` via `sys.executable`, with a hard timeout) because ddgs's native HTTP client, primp, can block forever while holding the GIL: on macOS two searches in threads at once froze the whole server. It fetches up to 8 pages in parallel through SSRF-guarded fetching (`_is_safe_public_host`, no redirects). `web_notes` takes one page per site. On forum pages (`_is_forum`), posters' own rigs ("my", "I use") are skipped and sentences must name the topic, or say someone used the gear on a thread about the topic. `_sentence_score` recognises gear by shape, not by a list of makes: a few generic equipment words (`_GEAR_WORDS`), model-like tokens (`_MODEL`: "VH4", "JC-40", minus decades and chords) and capitalised names (`_names`), plus use words (`_USE_WORDS`). Short spec lines ("JC-40: 40W stereo 2x10 combo", "Amplifier: Diezel VH4") count. Page text comes from trafilatura (`_main_text`, imported on first use by `_trafilatura`; forum pages include its "comments", which are the replies), falling back to `_PageText` when trafilatura is missing, raises or skips a short page. `_extract_evidence` splits it into blocks (`_content_blocks`, repeated sentences dropped), scores blocks from their sentences (`_block_score`), and returns up to `EVIDENCE_BLOCKS` of the best, trimmed to their scoring sentences and what they depend on (`_evidence_part`), plus a date or qualifier from a neighbouring block (`_block_context`, `_context_part`), on one line within `EVIDENCE_CHARS`. The title only says what a page is about; it is never evidence. Every request is about instruments and gear, so a page or search snippet that never uses a word from `_MUSIC_WORDS` is not evidence ("AC30" also finds a Panasonic AG-AC30 camcorder; song titles find lyrics pages). `web_notes` also collapses whitespace, because the AI (`ai._whole_lines`) and the page (`researchNotes`) read one source per line. A note from a search snippet, when the page can't be read, starts "Search snippet only:". Don't fix research by adding brands or models to these lists; compare runs with `scripts/eval_research.py`. `search` and `evidence` are injectable for tests.
- `tonesearch/overrides.py` holds per-request visitor settings from the Settings dialog, sent as `X-AI-*` and `X-TONE3000-Key` headers and stored only in the browser. `app.before_request` activates them on every request. When a visitor sets `X-AI-Provider`, `ai.config()` uses only the visitor's values and never falls back to the server's secrets. Visitors can choose only `cloudflare` or `custom`, not `local`, and a custom URL must be a public https host with redirects refused. Visitors can send AI tuning as `X-AI-*` headers, but it only takes effect with their own provider. Visitors who bring their own keys skip the hourly limits.
- `ai.gear_summary` passes the gear levels and requirements to `rank_packs`. `research._QUALIFIER` keeps sentences such as "modern equivalent" or "our catalogue only has two songs" in the evidence. The admin gear format is `kind | name | role | confidence`.
- Plans carry `aliases`, from the same AI call: the model's `aliases` (other names, only for artist, band, song or album requests, `ai._ALIAS_RULE`) plus its `keywords` (other wordings of any request, `ai._KEYWORD_RULE`), merged by `ai.filter_aliases`. They are what later searches match on, so sound and needs requests get keywords too. They're stored on library entries (`aliases` column, comma-separated, cleaned by `knowledge.clean_aliases`) and inside saved answers. `knowledge.match_score` is the one matcher for the library and for saved answers (`knowledge.saved_answer`, used by the website's `_saved_answer_by_alias`, which narrows rows by key suffix in SQL, and MCP `_saved_answer`): identity-word overlap ≥ `MATCH_THRESHOLD`, or every identity word of the request (at least 2) found among the saved words plus aliases. `same_sound=True`, used for saved answers, also rejects requests with description words the saved topic lacks.
- Gear `confidence` is one scale (`ai.CONFIDENCE`: best, close, alternative; `ai.confidence_of` maps synonyms and the old confirmed/artist/suggested, and a missing level means close). Plans carry a `requirements` list; `gear_summary` tells the ranker to ignore the ones about the physical box (combo, speakers, weight), since a capture is only the sound. `rank_packs` judges what each pack captures, not every product its description mentions (a cab recorded with the requested mic is still a cab). An alias is kept when it shares a word with the request or the evidence names it (the research notes, or the plan's summary, advice and gear), because aliases file research for later visitors; a request for needs (with `requirements`) keeps only names that share a word with it. A keyword is kept when at least half its words are the request's own, which keeps artists out of a sound's keywords. Don't require aliases to repeat the request: the prompt asks for *other* names, so that drops them all. The rules live in `ai.filter_aliases`, shared by `plan_tone` and `ai.suggest_aliases` (used by `scripts/backfill_aliases.py`); the prompt text is `ai._ALIAS_RULE`. `plan_tone` leaves relevance to the model and the research: Python only drops names made only of category words (`_generic`, `_GENERIC_WORDS`), relabels amp-brand pedals (`_KNOWN_PEDALS`), never searches for gear of kind `mic` (recording gear is what captures are made with, not what they capture) and skips searches for gear the model calls a guitar unless the request wants guitar captures (`_WANTS_GUITAR`, which includes classical, nylon and direct input), labels an item `alternative` when its own role calls it one (`_STAND_IN`), puts searches for alternatives last and fills spare slots with uncovered amps (`_same_gear`). Don't add product lists to fix model mistakes; check prompt changes with `scripts/eval_plans.py`. Research extracts keep up to 1,400 characters per source, and `RESEARCH_CHARS` defaults to 7,000 to fit four. `ai._whole_lines` cuts research at a source boundary.
- `tonesearch/knowledge.py` is the research library: web notes plus the plan's gear, saved per topic in `$TONESEARCH_DATA_DIR/knowledge.sqlite3`. `find` reuses an entry when the Jaccard overlap of their `identity_words` (topic words without sound descriptions, `_DESCRIPTIONS`; a request with none matches nothing) is at least `MATCH_THRESHOLD`. Saved answers and feedback still key on all topic words. Approved entries never expire. Unreviewed ones expire after `TONESEARCH_LIBRARY_DAYS`, and flagged ones are skipped. `/api/search` calls `find` before `web_notes` and saves fresh research after `plan_tone`. MCP `web_research` looks the entry up once, then returns the website's saved answer for the same rig (`_saved_answer`, with votes applied), and uses the library too, through `mcp_server.library_path`, which `app.py` points at `DATA_DIR`. MCP `save_gear` lets the assistant fill an entry's empty gear list after fresh research. It keeps only gear the entry's notes name (`_named_in`), drops generic names and never overwrites. Visitors flag entries with `POST /api/library/<id>/flag`. The owner reviews entries at `/admin` (Basic auth with `TONESEARCH_ADMIN_PASSWORD`, off when unset; POSTs must come from the same origin). Deleting an entry (`app._delete_entry`) also deletes everything built on it: the saved answers, plans and rankings of every topic that used it (its own words, saved answers that name it, found under any alias, via `cache.answers_by_entry`, and votes on it) and those topics' votes (`feedback.forget`); `app._entry_links` works this out, and the page lists it before deleting. Single votes are deleted from the Feedback view. `scripts/reset_data.py` clears saved data (`--all --yes` for a fresh start; a dry run without `--yes`).
- `tonesearch/db.py` opens every SQLite connection (library, cache, votes, rate limits): each module's `_setup` creates its tables once per file per process, and runs again after a "no such table" error. Connections always close.
- `tonesearch/cache.py` holds saved answers in `knowledge.sqlite3`. Each read passes its own `max_age`: `CATALOGUE_SECONDS` (`TONESEARCH_CATALOGUE_HOURS`, 24) for TONE3000 search results and whole answers, which contain them; `AI_SECONDS` (`TONESEARCH_AI_CACHE_DAYS`, 30) for plans and rankings; `REFERENCE_SECONDS` (7 days) for pack file lists and lookups. Like the library, it's best-effort: a database error counts as a miss. `/api/search` saves the whole answer (`result:` key), the plan (`plan:`) and the ranking (`rank:`), each tagged with the topic's `words` so `forget_topic` can drop them all. It reuses them only for first searches (no history, no `reuse_plan`, not `fresh`), and never saves an answer that has warnings. Plan and answer keys end with `ai.PLAN_VERSION`: raise it whenever `plan_tone`'s rules change what a plan contains (aliases, gear, queries), or searches keep reusing plans made by the old rules for 30 days. `research.tone3000_search`, `tone3000_models` (names only, never download links) and `tone3000_lookup` take a `cache_db` and share the public catalogue data between visitors and MCP. Because a cached answer never reaches TONE3000, MCP `_check_key` verifies every caller's key, cached for an hour.
- `cache.count` adds to a per-day `activity` table, best-effort, for each step a search reuses or redoes (`app.ACTIVITY_EVENTS`; `cache.remember(..., event=)` counts catalogue hits). `/admin?view=activity` shows it.
- `tonesearch/feedback.py` stores ratings: one vote per voter, topic and target (`brief`, or a `pack`). Voters are a salted hash of the IP or MCP key. `apply_votes` nudges the AI's fit by 8 per net vote, capped at ±3 votes; `withVotes` in app.js matches it. A bad brief, from `/api/feedback` or MCP `rate_result`, flags the library entry and calls `forget_topic`. `/admin?view=feedback` shows the votes.
- `tonesearch/mcp_server.py` is TONE Search as an MCP server with no SDK. The client's own AI plans and ranks, so it makes no AI calls. `handle` answers one JSON-RPC message and serves two transports: the local stdio server (`python -m tonesearch.mcp_server`, unlimited, key from `TONE3000_API_KEY`) and the hosted `POST /mcp` in `app.py` (stateless JSON, key from `Authorization: Bearer`, `X-TONE3000-Key` or `?key=` for URL-only connectors, limited per hour by the `mcp` and `mcp_research` limits). The tools in `TOOLS` wrap `research.py`: `web_research`, `search_packs`, `lookup`, `list_pack_models` and `download_link`. `download_link` returns the pack's TONE3000 page. There is also a `find_tone` prompt. The caller's own `t3k_cs_` key is mandatory for every tool, `web_research` included. It is how callers are told apart from bots, so `_check_key` confirms it with TONE3000 before a web search and caches the answer for an hour. `call_tool` activates it through `overrides` so the server's key is never used, then clears it. Filter validation lives in `research.validate_filters`, which `app._search_filters` aliases.
- The frontend is `templates/index.html` plus `static/app.js` and `static/style.css`, with no build step.
- Cab embed (`/cab`, `templates/cab.html`, `static/cab.js`) learns a capture plus a cabinet IR as one A2 model on the visitor's own Kaggle account. The page has no ads because it holds Kaggle credentials (`X-Kaggle-Username`/`X-Kaggle-Key`, never stored). It previews in the browser with NeuralAmpModelerCore in WebAssembly (`static/vendor/nam-wasm`, an AudioWorklet; needs https or localhost), which normalises output to -18 dB from loudness metadata, so comparisons match levels first. `tonesearch/cab.py` checks the files (WaveNet or A2, 48 kHz, receptive field within `A2_RECEPTIVE_FIELD`; IR a PCM/float WAV up to `MAX_IR_SECONDS`) and builds the script by replacing the single `PAYLOAD = ""` line of `tonesearch/cab_kernel.py` with the files as gzipped JSON in base64. `cab_kernel.py` runs on Kaggle, so it must stay self-contained (stdlib at import; numpy, scipy, soundfile, torch and the pinned neural-amp-modeler inside functions). It mirrors NAM Mixer's learned cab embed (IR prep, -0.2 dBFS ceiling, epoch presets, metadata) and converts classic A1 layer configs with `modern_wavenet`, because neural-amp-modeler 0.13's `init_from_nam` only reads the new layout. `tonesearch/kaggle.py` calls `https://api.kaggle.com/v1/<service>/<method>` (the endpoints kagglesdk uses) with Bearer auth for `KGAT_` tokens and Basic auth for legacy keys; `push_script` sends `SaveKernel` with the script text and a T4. NAM's training input comes from `TONESEARCH_NAM_INPUT_URL` (downloaded by the notebook; the URL travels in the payload) or the public Kaggle dataset in `TONESEARCH_NAM_INPUT_DATASET` (attached, tried first); the notebook checks its MD5 either way, and training is off when neither is set. Job slugs come from `cab.job_slug`, never visitor text.

`/api/search` runs this pipeline:
1. Optionally gather web notes.
2. `ai.plan_tone` produces a summary and search queries.
3. `tone3000_search` runs for each query; results are deduplicated.
4. The results are cut to 12, taking turns between the queries (best first by the chosen sort within each) so one piece of gear can't fill the list; small models stop scoring partway through long lists.
5. `ai.rank_packs` assigns `ai_fit`/`ai_why`.

Each search and pack question has an overall budget, `app.REQUEST_BUDGET_SECONDS` (85s, env `TONESEARCH_REQUEST_BUDGET_SECONDS`), because Cloudflare's proxy ends requests after about 100s. `plan_tone` must finish `RANKING_RESERVE_SECONDS` early, and ranking is skipped with a warning when under 8s remain. Failures in web research, TONE3000, or ranking become `warnings` rather than errors. Only a failure in `plan_tone` returns an error, a 503. Upstream failures use 503 rather than 502 because Cloudflare replaces the body of a 502 with its own page.

Search filters (`research.DEFAULT_FILTERS`) are validated by `app._search_filters` and mapped to the API's separators by `research._search_params`: gears and tags use `_`, sizes use `-`, creators use `,`. The UI's "Apply to results" and tag clicks send `reuse_plan`, the previous summary and queries, which skips research and `plan_tone`. `/api/lookup/<makes|tags|creators>` provides autocomplete, cached for an hour in `LOOKUP_CACHE`, with its own `lookup` hourly limit. `/api/packs/<id>/download` zips the pack's files on the server with `research.tone3000_pack_zip`, because TONE3000's own whole-pack link is only for approved partners with a user sign-in. `/api/packs/<id>/models` takes an `architecture` parameter.

`/api/pack_chat` answers questions about one pack with `ai.ask_about_pack`, passing the pack's model file names as context.

## Conventions

- Network functions accept an `opener=urlopen` parameter so tests can inject fakes; tests never hit the network. `tests/test_app.py` monkeypatches `app_module.DATA_DIR` to `tmp_path` and clears the `NAM_MIXER_AI_*` env vars.
- Routes catch `RuntimeError` from the service modules and turn it into user-facing JSON errors. Services should raise `RuntimeError`/`AiError` with readable messages.
